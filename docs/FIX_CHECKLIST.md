# 修复与迭代清单

> 基于 Godot 4.7.2 静态审阅与无窗口运行时烟测整理。
>
> 当前基线：项目导入、菜单启动、战斗场景启动、地图解析、建造、出兵、第一波结算和祝福选择均可运行；功能烟测结果为 **21 PASS / 2 FAIL**。

## 执行原则

- 按 `P0 → P1 → P2` 顺序处理；P0 未完成前不进行大规模数值平衡或内容扩充。
- 每修复一项，先增加能复现问题的自动化测试，再修改实现。
- 完成项必须同时满足“验收标准”，不能只以场景不报错作为通过依据。
- 当前真实规则以源码和 Catalog 为准；修改玩法语义时同步更新 README 与设计文档。

## P0：阻断性与战斗正确性

### [x] P0-01 修复数字键只更新 HUD、不更新实际建筑选择

- **现象**：按 `1-6` 后按钮高亮改变，但 `_selected_build_id` 仍可能保留旧值。
- **涉及文件**：`scripts/game/game.gd`、`scripts/ui/hud.gd`
- **修复建议**：数字键分支调用统一的建筑选择入口，确保 HUD 状态、地图预览和 `_selected_build_id` 同步；避免维护两套选择逻辑。
- **验收标准**：
  - 依次按下 `1-6`，实际选择 ID 与 `BuildCatalog.ORDER` 一致。
  - 每次选择后建造出的类型与 HUD 高亮一致。
  - 鼠标点击建造按钮仍保持原行为。
- **回归测试**：`input_selection_test.gd`

### [x] P0-02 修复最后一只精英死亡时不生成附魔掉落

- **现象**：最后一只敌人死亡会先触发波次结束，阶段由 `COMBAT` 变为 `SETTLEMENT`，随后掉落条件失败。
- **涉及文件**：`scripts/game/game.gd`
- **修复建议**：在通知 WaveManager 敌人离场前生成精英掉落，或使用死亡发生时捕获的战斗阶段决定是否生成，避免同步信号改变阶段后再判断。
- **验收标准**：
  - 普通精英死亡时生成一个掉落物。
  - 精英作为本波最后一只敌人死亡时仍生成一个掉落物。
  - 同一精英不会重复生成掉落。
  - 明确第 10 波 Boss 是否掉落；若掉落，胜利后必须存在可消费窗口。
- **回归测试**：`elite_drop_test.gd`

### [x] P0-03 修复敌人索敌与攻击距离的错误缩放

- **现象**：敌人使用 `Metrics.art()` 缩放战斗距离，45～62 px 的距离实际被压缩到约 7～10 px。
- **涉及文件**：`scripts/entities/enemy.gd`、`scripts/game/game_metrics.gd`
- **修复建议**：绘制尺寸继续使用 `Metrics.art()`，索敌、攻击和移动相关距离统一使用 `Metrics.combat_range()`；全局检索所有距离换算，避免同类问题残留。
- **验收标准**：
  - 敌人在 Catalog 规定的距离内能发现并攻击友军、英雄和建筑。
  - 超出接敌范围后恢复沿路径移动。
  - 不出现隔着明显超远距离攻击的情况。
  - 兵营单位能够稳定承担拦截作用。
- **回归测试**：`enemy_engagement_range_test.gd`

### [x] P0-04 让附魔选择真正暂停战斗

- **现象**：`ENCHANT` 阶段只暂停 WaveManager；已有敌人、塔、英雄和投射物仍运行，友军可能开始撤退。
- **涉及文件**：`scripts/game/game.gd`、各战斗实体脚本
- **修复建议**：建立统一的战斗暂停接口。可使用独立战斗节点的 `process_mode`，或由关卡向实体广播暂停状态；HUD 必须保持可交互。
- **验收标准**：
  - 附魔弹窗打开后，敌人和友军位置、生命、攻击冷却均不变化。
  - 不继续生成敌人，不继续处理投射物伤害。
  - 选择附魔后所有系统从原状态继续运行。
  - 暂停期间友军不会切换为驻扎行为。
- **回归测试**：`phase_pause_test.gd`

### [x] P0-05 结束状态停止全部战斗模拟

- **现象**：进入 `FINISHED` 后只显示结算弹窗，场上单位仍可能移动、攻击或处理事件。
- **涉及文件**：`scripts/game/game.gd`、`scripts/game/wave_manager.gd`
- **修复建议**：抽取统一的 `_stop_combat_simulation()`，由胜利和失败共同调用；停止波次并冻结战斗节点，但保留结算 UI、重开和返回菜单操作。
- **验收标准**：
  - 胜利或失败后不再生成敌人。
  - 所有单位、投射物和伤害结算停止。
  - 结果弹窗仍可正常选择重开或返回菜单。
  - 重开后不存在上一局残留状态。
- **回归测试**：`finished_phase_test.gd`

### [x] P0-06 修正英雄 R 技能的成功返回值

- **现象**：范围内没有目标时，`try_cast_skill("freeze")` 仍返回成功，但实际没有进入冷却。
- **涉及文件**：`scripts/entities/hero.gd`、`scripts/game/game.gd`
- **修复建议**：让冻结实现返回是否命中并成功施法；只有成功时才进入冷却和显示成功提示。
- **验收标准**：
  - 无目标时返回失败，不进入冷却，HUD 不显示“释放成功”。
  - 有合法目标时返回成功、施加冻结并进入冷却。
- **回归测试**：`hero_skill_test.gd`

- **验收标准**：所有测试脚本已纳入版本管理；README 中的命令在新克隆项目上可以直接执行；任一断言失败时进程返回非零退出码。

### [ ] P1-02 闭合冰晶与附魔经济

- **现象**：冰晶会累计和显示，但附魔由点击掉落免费触发，当前没有冰晶消费逻辑。
- **涉及文件**：`scripts/game/game.gd`、`scripts/game/upgrade_manager.gd`、`scripts/ui/hud.gd`、相关设计文档
- **需要决策**：
  - 方案 A：掉落物直接提供一次附魔，删除冰晶余额。
  - 方案 B：掉落只增加冰晶，消费固定数量开启附魔。
  - 方案 C：冰晶作为跨关资源，当前单关不在波末赠送。
- **验收标准**：资源来源、用途、消费时点和 Boss 奖励均有唯一明确规则；UI 与实际行为一致。

### [x] P1-03 限制准备阶段无限经济

- **现象**：准备阶段可无限恢复冻气，挂机能够消除经济压力。
- **涉及文件**：`scripts/game/game.gd`、`scripts/ui/hud.gd`、`docs/BALANCE.md`
- **已采用方案**：准备阶段不再产生冻气；每个非最终波选择祝福后发放 `16 + 4 × (波次序号 - 1)` 的基础冻气奖励，并受波末奖励倍率影响。
- **验收标准**：等待时间不能产生无限资源；玩家仍有合理的调整阵型和回血窗口；规则在 HUD 中可被理解。

### [ ] P1-04 明确第 10 波胜利条件

- **现象**：当前只要第 10 波所有敌人离场就可能胜利，灵梦漏过但琪露诺存活时也可能判胜。
- **涉及文件**：`scripts/game/game.gd`、`scripts/data/wave_catalog.gd`、设计文档
- **需要决策**：胜利要求“灵梦被击败”，还是只要求“琪露诺在第 10 波后存活”。
- **验收标准**：击杀 Boss、Boss 漏怪、Boss 击杀英雄三条路径都有自动化测试，结算结果符合统一规则。

### [x] P1-05 修正生命上限祝福的双重治疗

- **现象**：提升生命上限时 `update_modifiers()` 自动补充上限差值，随后 `heal_now` 可能再次治疗。
- **涉及文件**：`scripts/entities/hero.gd`、`scripts/game/game.gd`、`scripts/data/upgrade_catalog.gd`
- **验收标准**：每层祝福的生命上限提升和即时治疗严格符合 Catalog 描述；满血、残血和濒死状态均测试。

### [x] P1-06 修正建造预览与实际占地判定不一致

- **现象**：预览主要检查地图格属性，建筑重叠位置可能显示可建造，点击后才被拒绝。
- **涉及文件**：`scripts/game/map_view.gd`、`scripts/game/game.gd`
- **修复建议**：由关卡把占用格查询传给 MapView，或让预览调用与实际建造相同的 footprint 校验函数。
- **验收标准**：道路、核心、边界和建筑重叠四种非法位置均显示一致的不可建造反馈。

### [x] P1-07 统一手动指定目标规则

- **现象**：兵营基类接受指令但不执行；英雄被框选后不能接收攻击指令；友军可能跨地图追逐手动目标。
- **涉及文件**：`scripts/game/game.gd`、`scripts/entities/defense_structure.gd`、`scripts/entities/ally_unit.gd`、`scripts/entities/hero.gd`
- **验收标准**：明确哪些单位支持优先目标；不支持的对象不计入“已指定数量”；目标离开允许范围或失效后恢复自动索敌。

## P2：架构、性能与内容生产

### [ ] P2-01 拆分 `game.gd`

- **现象**：关卡根同时承担阶段、输入、建造、选择、经济、掉落和结算职责。
- **建议模块**：`BuildController`、`SelectionController`、`BattleFlowController`、`RewardController`。
- **验收标准**：拆分前后的自动化测试全部通过；关卡根只负责组合和跨系统协调。

### [ ] P2-02 优化单位索敌

- **现象**：实体频繁调用 `get_nodes_in_group()` 全量扫描，单位规模扩大后成本较高。
- **建议顺序**：关卡维护存活数组 → 降低并错开扫描频率 → 达到性能瓶颈后再引入空间网格。
- **验收标准**：建立含固定单位规模的性能基线；优化后行为不变且帧耗时可量化下降。

### [ ] P2-03 将 Catalog 迁移为类型化 Resource

- **现象**：大量弱类型 `Dictionary` 依赖字符串字段，缺少编辑器校验。
- **建议资源**：`TowerDefinition`、`BarracksDefinition`、`AllyDefinition`、`EnemyDefinition`、`WaveDefinition`、`ModifierDefinition`。
- **验收标准**：关键字段有类型和默认值；资源缺失或非法时给出明确错误；现有数值能无损迁移。

### [ ] P2-04 引入 PackedScene 与对象复用

- **现状**：英雄、敌人、建筑、投射物和特效全部通过脚本动态创建。
- **建议**：正式美术接入时迁移到 PackedScene；对高频投射物和命中特效评估对象池。
- **验收标准**：逻辑数据与表现节点解耦；替换美术不要求修改 Catalog 的战斗字段。

### [ ] P2-05 建立可复现的随机局

- **现象**：强化随机数每次启动自动随机化，不利于复现问题和测试。
- **涉及文件**：`scripts/game/upgrade_manager.gd`
- **修复建议**：支持从会话或测试注入种子，并在调试界面或日志显示本局种子。
- **验收标准**：相同种子产生相同强化序列；正式游戏仍可默认生成随机种子。

### [ ] P2-06 完成数值与可玩性验证

- **前置条件**：全部 P0 完成，冰晶和准备阶段经济规则确定。
- **需要记录**：每波时长、通关率、平均剩余生命、建造组合、冻气收支、各单位伤害与承伤占比。
- **重点问题**：第 2 波数量骤增、东路长度、兵营拦截能力、范围塔收益、Boss 漏怪结果。
- **验收标准**：使用至少三套典型构筑完成全十波测试，并基于数据而非体感调整 Catalog。

## 每次提交的最低回归要求

```powershell
godot --headless --editor --path . --quit
```

随后运行已提交的自动化测试，至少覆盖：

- 项目及脚本可以导入；
- 菜单和战斗场景可以实例化；
- 塔和兵营可以建造；
- 第一波能生成并结束；
- 精英作为最后一只敌人时仍能正确处理掉落；
- 附魔、结算和结束阶段不会继续模拟战斗；
- 数字键选择与 HUD、建造结果一致。
